# 本机传输：UDS + smux_v1 + mptp_rpc

- 日期：2026-11-05 03:45
- 状态：**当前实现说明**（不是迁移计划，也不是历史记录）。

---

## 0. 一句话

`kb_core` 与客户端之间的本机通信是：

```text
Unix domain socket + smux_v1 多路复用 + mptp_rpc 按域 RPC
```

跨机时，`kb_core_rproxy` 在 TCP 与同一套 typed RPC 之间做转换。

---

## 1. 为什么是这套

| 需求 | 选择 | 原因 |
| :--- | :--- | :--- |
| 本机端点 | **UDS** | 文件系统权限（0600）、无需端口分配、Linux 上可靠 |
| 一条连接上的多路请求 | **smux_v1** | 一个子流一次调用，天然隔离请求；框架自带窗口/背压 |
| RPC 形状 | **mptp_rpc** | `#[rpc]` 宏生成 interface / service / 客户端代理 / 服务端派发；按业务域拆 service |
| 编解码 | **denco（MessagePack）** | 与本机 RPC body、TCP 帧、本地存储同一套；协议类型只保留 denco 派生 |

当前依赖树里没有 ipc-channel / postcard / serde。

## 2. 分层

```text
┌─────────────────────────────────────────────────────────────┐
│ 调用方：kb_admin_desktop / kb_core_rproxy / 测试            │
├─────────────────────────────────────────────────────────────┤
│ kb_client_conn_mgr（连接管理、应用层 Hello）                 │
│   └─ kb_svc_mptp_ipc::Client（Send+Sync，同步 connect）     │
│        └─ 宿主线程：compio Runtime + 作业队列 + MptpClient   │
├─────────────────────────────────────────────────────────────┤
│ UDS（kb-<日期>-<uuid>.sock）                                 │
├─────────────────────────────────────────────────────────────┤
│ kb_svc_mptp_ipc::Listener / Connection（smux + MptpServer）  │
│   └─ kb_core::ipc_ 的四个按域 service                        │
├─────────────────────────────────────────────────────────────┤
│ abs_kb_svc_v1_desktop_rpc（#[rpc] 契约、错误映射）           │
├─────────────────────────────────────────────────────────────┤
│ abs_kb_svc_v1_desktop（业务数据） + abs_kb_core_handshake    │
└─────────────────────────────────────────────────────────────┘
```

## 3. 端点与系统层握手

### 3.1 `kb_core` 侧

```text
Listener::bind(runtime_dir).await
  → create_dir_all(runtime_dir)
  → 清理残留 kb-*.sock / kb-*.ipc
  → 生成 kb-<YYYYMMDD>-<uuid>.sock
  → UnixListener::bind(path).await
  → chmod 0600
announce_ipc_name_file()
  → stdout 一行 IpcReadyNotice（json_denco）
loop { accept().await; connection.serve(services).await }
```

- 文件名由 `kb_core` 决定，每次启动独一无二；
- 同时清理运行时目录里的 `.ipc` 残留；
- `IpcReadyNotice.ipc_name_file` 字段名保留（消息兼容），**语义是 socket 路径**；
- `--handshake-prompt stdio` 才打这一行；默认 `none`。

### 3.2 客户端侧

```text
Client::connect_with_timeout(runtime_dir, timeout)
  → 宿主线程：扫描最新的 kb-*.sock（file_type().is_socket()）
  → UnixStream::connect(path).await（重试 + 总超时）
  → smux HandshakeAgent::invite_async
  → MuxConnection → MptpClient
```

- `connect` 是**同步**调用（阻塞在调用方线程，内部由宿主线程完成异步连接）；
- 连接成功后 `Client` 是 `Send + Sync`，可以放进全局单例；
- 拿到通知之后仍可能短暂连不上：服务端可能还没 `accept`，所以客户端带重试。

## 4. 线程 / 运行时模型

| 位置 | 运行时 | 说明 |
| :--- | :--- | :--- |
| `kb_core` 主线程 | compio（`#[compio::main]`） | `Listener::bind/accept`、`Connection::serve`、`Store` 的 `compio::fs` |
| `Client` 宿主线程 | 独立 compio Runtime | 一条连接一条线程；UDS connect、smux 握手、MptpClient、作业循环 |
| 调用方线程（FRB / rproxy / 测试） | 无要求 | 只提交 Job + 等 oneshot；可用 `futures_lite::block_on` |

> 服务端 API 是 compio 绑定的；客户端 API 是运行时无关的。这个不对称是刻意的：
> 服务端只跑在 `kb_core` 里，客户端要被多种调用方复用。

**future 里禁止阻塞**：所有阻塞等待都收敛到专职线程；调用方拿到的 future 只轮询
完成量与取消令牌。

## 5. RPC 契约

契约 crate：`abs_kb_svc_v1_desktop_rpc`。

```rust
#[rpc(
    path = "kb/v1",
    services = [TrHandshake, TrWorkspaceService, TrSessionService, TrGeneration]
)]
pub struct KbApiV1;
```

| 方法路径 | 方法 | 入参 | 出参 |
| :--- | :--- | :--- | :--- |
| `/kb/v1/handshake` | `hello` | `ClientInfo` | `ServerInfo` |
| `/kb/v1/workspace` | `list_workspaces` | – | `WorkspaceList` |
| | `add_workspace` | `AddWorkspaceRequest` | `Workspace` |
| | `remove_workspace` | `WorkspaceId` | `Ack` |
| | `rename_workspace` | `WorkspaceId`, `String` | `Workspace` |
| `/kb/v1/session` | `list_sessions` | `WorkspaceId` | `SessionList` |
| | `create_session` | `CreateSessionRequest` | `SessionSummary` |
| | `get_session` | `WorkspaceId`, `SessionId` | `SessionDetail` |
| | `remove_session` | `WorkspaceId`, `SessionId` | `Ack` |
| | `rename_session` | `WorkspaceId`, `SessionId`, `String` | `SessionSummary` |
| `/kb/v1/generation` | `ask` | `AskRequest` | `SessionDetail` |

- body 用 `mp_denco`；
- 每个方法都返回 `impl TrMayCancel<MayCancelOutput = RpcResult<T>>`；
- 调用方既能 `.await`，也能 `.may_cancel_with(token).await`；
- `Ack` 代替 `()`（denco 目前不支持空类型）。

## 6. 业务错误怎么过线

不改 mptp_rpc 上游，用“专用状态码 + 客户端剥离 Display 前缀”保真：

```text
服务端：ErrorCode → 460..=466 状态码
        ErrorReply.message 原样放进 RpcError::Service.message
客户端：从 RpcError::Remote.body 取第一个 "）：" 之后的内容
        还原 ErrorReply { code, message }
```

- 460–466 的映射由 `abs_kb_svc_v1_desktop_rpc::status_of_error_code` 定义；
- 前缀格式由一条单元测试钉住；上游文案变化时测试先红；
- 还原后统一是 `KbRpcError::Business(ErrorReply)`；
- 其它 RPC 错误 → `KbRpcError::Transport(具体传输错误)`。

业务失败与传输失败**分成两个变体**，调用方据此决定“提示用户”还是“重试 / 换连接”。

## 7. 取消

- 取消令牌由调用方给（例如 `TimeoutToken`）；
- `Client` 的每个方法在等待完成量时同时轮询取消 future；
- **取消只放弃等待，不撤回请求**：请求仍会被服务端处理；宿主线程用不可取消令牌
  把它跑完；
- 服务端 `ipc_` 把请求带的令牌继续传给 `Store`，`Store` 的每个操作都检查它；
- 取消的落点统一是 `Transport(Cancelled)` / `StoreError::Cancelled`，不是业务错误。

---

## 8. 背压

- 本机 MPTP：由 `smux_v1` 的子流窗口与 MPI 层的流控承担；调用方不应假定
  “send 永不阻塞”；
- 跨机 TCP：`kb_core_rproxy` 在上行用 64 KiB 有界通道，满了就停读 socket，
  TCP 窗口自然关上；
- 业务层如果还有“同一会话同时只允许一轮”之类的约束，由业务语义表达，
  不能依赖传输层。

---

## 9. 已知边界

| 限制 | 说明 |
| :--- | :--- |
| 事件推送 | 没有实现；`Event` 类型保留 |
| 流式生成 / `Cancel` | 没有实现；`ask` 是同步一问一答 |
| 并发服务多客户端 | `kb_core` 一次只服务一个连接 |
| Windows 命名管道 | 没有实现；compio 的 UDS 是 Unix 专用 |
| 鉴权 / TLS | 没有；跨机只用于受信网络 |
| 旧数据 | 存储是 `.mp`，不读旧的 `.json` |
