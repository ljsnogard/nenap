# 用 UDS + mptp_rpc 替换 kb_svc_servo_ipc 的迁移计划（v2）

- 日期：2026-11-04 21:29（v1）/ 2026-11-04 21:44（v2 修订）
- 状态：**已实施（P0–P8）**；实际结果与偏差见 §15
- v2 的两条新硬约束：
  1. **协议实现完全移除 serde，只使用 denco**；`abs_llm` 等数据 crate 最终不得依赖 serde；
  2. **本轮不能改动 mptp_rpc 上游**（`RpcError::wire_message` 之类的改动留到以后）。
- 前置事实：**当前 HEAD `c73ea0f` 不能编译**（WIP denco 迁移，见 §3.3），P0 先修。

## 0. 结论摘要

把本机 IPC 从「ipc-channel + 三条通道 + 信封」换成
「Unix domain socket + `smux_v1` + `mptp_rpc` 的按业务域 unary RPC」，同时把**所有协议编解码统一到 denco**：

| 用途 | v1（serde / postcard） | v2（denco） |
| :--- | :--- | :--- |
| 本机 MPTP RPC body | postcard（ipc-channel 内部） | `mp_denco`（MessagePack） |
| 跨机 TCP 帧载荷 | postcard | `mp_denco` |
| 本地文件存储 | `serde_json` | `mp_denco`（扩展名改 `.mp`；不兼容旧 JSON） |
| stdout 就绪通知 | `serde_json` | `json_denco`（仍是文本 JSON） |
| 用户可编辑配置（TOML） | serde + toml | **保留**（非协议；待定） |
| rig 插件解析第三方 JSON | serde_json | **保留**（rig 本身依赖 serde；待定） |

- `kb_core` 直接 bind `kb-<日期>-<uuid>.sock`，用 `MptpServer` 在默认垛口 `0x80` 服务；
- 新传输 crate `kb_svc_mptp_ipc` 提供 `Listener` / `Connection` / `Client`；
  `Client` 自带宿主线程（compio Runtime + 作业队列），对外仍是 `Send + Sync`、`connect` 同步；
- **业务错误仍走 `RpcError`**，因为不能改上游：服务端用 460–466 专用状态码，
  客户端按 `RpcError::Service` 的 Display 前缀剥离出原始 `ErrorReply.message`（§5.4）；
- 事件推送本轮不做；`Event` 类型保留，并随 TCP 帧一起改成 denco 编码；
- **不保证旧存储数据可读**：存储从 serde_json 换成 `mp_denco`，扩展名改为 `.mp`，
  旧 `.json` 文件不再读取（用户数据若需保留，另行一次性迁移）。

## 1. 目标与非目标

### 1.1 目标

1. 本机信道改为 **UDS**；
2. 应用层协议由 `mptp_rpc/rpc_core_v1` 的 `#[rpc]` 承载，**按业务域拆 service**；
3. **协议实现零 serde**：`abs_kb_svc_v1_desktop`、`abs_llm`、`abs_kb_core_handshake`、
   `kb_core_rproxy_wire`、`kb_core`、`kb_core_starter` 都不再依赖 serde/postcard/serde_json；
4. 删除 `kb_svc_servo_ipc`，全仓不再依赖 `ipc-channel`；
5. `kb_core_starter` 职责不变（起进程 + 读 stdout 通知），只改文档与解析实现；
6. 业务消息（`Workspace` / `SessionDetail` / `AskRequest` / `ErrorReply` / `Event` / …）
   类型与字段不变。

### 1.2 非目标（本轮不做）

| 项 | 理由 |
| :--- | :--- |
| 服务端 → 客户端的事件推送 | 已拍板暂缓；`rpc_core_v1` Phase 1 unary 不带同会话推送 |
| 多客户端**并发**服务 | 保持「一次一个连接」 |
| 流式生成、`Request::Cancel` | 现有 `ask` 是同步一问一答 |
| 鉴权 / TLS | 与现状一致 |
| Windows 命名管道 | compio 的 UDS 是 Unix 专用 |
| Dart/Flutter 侧 API | FRB 的扁平 DTO 与 Dart 调用形状不变 |
| 改 mptp_rpc 上游 | 本会话硬约束 |

## 3. 现状与约束

### 3.1 当前本机 IPC 的形状（`kb_svc_servo_ipc`）

```text
kb_core（服务端）                          kb_admin_desktop / rproxy（客户端）
───────────────                           ──────────────────────
Listener::bind(runtime_dir)                Client::connect(runtime_dir)
  → <dir>/kb-<日期>-<uuid>.ipc               → 扫名字文件、读端点名、重试
  → IpcOneShotServer（临时目录 socket）       → 建三条 ipc-channel 通道
  → 把端点名写进名字文件                      → 发引导消息（请求/应答/事件三元组）
  → accept（阻塞，spawn_blocking）            → 专用路由线程按 request_id 配应答
Connection::serve(&service)                Client: impl 各按域 trait
  → 逐条 dispatch_ Request → Reply            → 每个方法造信封、等应答、翻载荷
```

- ipc-channel 0.23 的内部编解码器是 **postcard（serde）**，所以旧路径必须保留 serde 派生；
- 端点名字文件由 `kb_core` 决定，文件**内容**才是可连端点；
- 事件通道已开好但当前没有真实推送。

### 3.2 目标机制的关键事实（mptp_rpc / denco / smux_v1）

| 事实 | 影响 |
| :--- | :--- |
| `rpc_core_v1` body 编码是 **denco + MessagePack** | 业务类型必须实现 `TrEncodable` / `TrDecodableOwned` |
| `#[rpc]` 方法返回 `impl TrMayCancel<'f, MayCancelOutput = RpcResult<T>>` | 旧 GAT trait 要重写；`T` 不能是 `()` |
| 路径 = `/{interface}/{service}`，方法名只在 body enum | 一条子流 = 一次调用；方法/字段顺序是**线上契约**（只应末尾追加） |
| `rpc_core_v1` 默认 feature `rt-tokio` | 必须关默认，只点亮 `rt-compio` |
| 运行时由 `abs_art-facade` 在**每个进程自己的依赖图**里选定 | 同一进程内要一致；跨进程（插件）互不影响；业务代码优先用 facade，只有网络/文件系统才直接用运行时 API |
| 句柄操作必须在所选后端运行时上下文内 | 客户端自带宿主线程；服务端本来就在 `#[compio::main]` |
| `smux_v1_uds_bench/src/rt_compio.rs` 有 compio+UDS 装配 | 直接照抄 `UnixListener::bind(...).await`、`BuffRead/BuffWrite::try_new`、`HandshakeAgent` |
| `MptpServer` handler 收 `ChannelTx/Rx` 按值，收尾由 handler 负责 | 由 `RpcRouter`/`RpcCallCtx` 承担 |
| 同一 impl 类型在同一 interface 下只能有一个 `TrRpcService` | 四个业务域需要四个薄包装类型（§5.3） |
| `RpcError::Service` 的 Display 会给 message 加前缀 | 不能改上游 → 业务错误用 460–466 状态码 + 客户端剥离前缀（§5.4） |

### 3.3 基线是红的（P0 必须先修）

`HEAD c73ea0f`（`Start replace serde with denco`）是半成品：

- `abs_kb_core_handshake`：把 stdout JSON 通知改成了 denco 派生，但
  - 它是 **stdout 上的一行 JSON**，由 `kb_core_starter` 用 `serde_json` 解析，不是 MPTP 线上；
  - `#[serde(rename = "ipc_ready")]` 与 serde 依赖被删，发/收两端都编不过；
  - derive 导入、`std::String`、`TrStringView` 路径都有错。
- `abs_llm`：删了 serde 依赖却保留 `Serialize, Deserialize` 派生；`abs_mm::mem_alloc` 路径也失效。
- `abs_kb_svc_v1_desktop`：`TurnState` 的 `rename_all` 被删，会改变落盘 JSON 与 Dart 侧取值。

**P0 的取向**：先做**定向修复**恢复绿基线（保留 serde 作为过渡），而不是直接完成
serde 移除——因为旧 ipc-channel 路径仍需要 serde（见 Q1）。

### 3.4 denco 编解码器与属性

| 需求 | denco 方案 |
| :--- | :--- |
| MessagePack | `mp_denco::{MpEncoder, MpDecoder}`（RPC body / TCP 帧 / 存储） |
| JSON | `json_denco::{JsonEncoder, JsonDecoder}`（仅 stdout 通知与 CLI 展示） |
| `#[serde(transparent)]` | `#[denco(transparent)]`（所有 id newtype、`Capabilities(u8)`） |
| `#[serde(rename_all = "...")]` | `#[denco(rename_all = "...")]`（只为可读性，不再是兼容要求） |
| `#[serde(rename = "...")]` | `#[denco(rename = "...")]`（`IpcReady` → `"ipc_ready"`） |
| `#[serde(default)]` | 不再需要（存储是位置编码的 MessagePack，旧数据不读） |
| 内部标签 / `skip_serializing_if` | 不再使用；JSON 走外部标签，MessagePack 走位置编码 |

编码到 `Vec<u8>` 的辅助（denco 是流式、异步的）：
用一个可增长的 `&mut [u8]` 循环——先 64 KiB，编码失败且缓冲区已空就翻倍，上限 64 MiB。
**存储与 TCP 帧都用 MessagePack**；`json_denco` 只用于 stdout 通知与 CLI 展示。

│   └─ kb_core::ipc_（四个薄包装 service）                      │

### 4.2 一次调用怎么走

```text
客户端调用 client.list_workspaces()
  → WaitAsync：造 Job（闭包，捕获请求与 oneshot sender）
  → 投递到宿主线程的作业队列
宿主线程（compio Runtime，连接就在这里建）
  → ClientProxy<KbApiV1>.list_workspaces().await
  → MPTP Call /kb/v1/workspace（一条子流）
服务端 kb_core（compio 主运行时）
  → MptpServer 收子流 → Router → RpcRouter<KbApiV1> → KbWorkspace::list_workspaces
  → 读 Store → Ok(WorkspaceList)，或 RpcError::Service { status: 460+code, message }
客户端宿主线程
  → Ok(v) → oneshot；或 Remote{status,body} → 剥离前缀 → KbError::Business(ErrorReply)
  → 调用方 WaitAsync 完成
```

### 4.3 线程 / 运行时模型

| 位置 | 运行时 | 说明 |
| :--- | :--- | :--- |
| `kb_core` 主线程 | compio（`#[compio::main]`） | `Listener::bind/accept`、`Connection::serve`、Store 的 `compio::fs` |
| `Client` 宿主线程 | 独立 compio Runtime | 一条线程一条连接；UDS connect、smux 握手、MptpClient、作业循环 |
| 调用方线程（FRB / rproxy / 测试） | 无要求 | 只提交 Job + 等 oneshot；可用 `futures_lite::block_on` |

> 服务端 API 是 compio 绑定的（`Listener::bind/accept` 必须在 compio 上下文里 await），
> 客户端 API 是运行时无关的。这个不对称要写进 crate 文档。

### 4.4 端点与引导

```text
kb_core 启动：
  Listener::bind(runtime_dir).await
    → create_dir_all
    → 清理残留 kb-*.sock / kb-*.ipc
    → 生成 kb-<YYYYMMDD>-<uuid>.sock
    → compio::net::UnixListener::bind(path).await
    → chmod 0600
  announce_ipc_name_file()   // stdout 一行 IpcReadyNotice JSON（json_denco）
loop {
  let conn = listener.accept().await?;   // 内含 smux 握手
  conn.serve(services).await?;           // 内含 MptpServer
}

客户端：
  Client::connect(runtime_dir)（同步）
    → 宿主线程：扫描最新的 kb-*.sock（file_type().is_socket()）
    → UnixStream::connect(path).await（重试 + 总超时）
    → smux HandshakeAgent::invite_async
    → MuxConnection → MptpClient
```

`IpcReadyNotice.ipc_name_file` 字段名不改（消息兼容），语义改为 socket 路径；
`kb_core_starter::Launched::name_file()` 保持名字，文档说明它现在是 socket 路径。

## 5. RPC 契约与编解码

### 5.1 新 crate：`kb_svc/crates/abs_kb_svc_v1_desktop_rpc`

职责：`#[rpc]` 契约、`KbRpcError`、状态码 ↔ `ErrorCode` 映射、interface 标记。
依赖：`abs_kb_svc_v1_desktop`、`abs_cancel`、`denco_macro`、`rpc_core_v1`、`rpc_svc_macro`。

> 数据 crate `abs_kb_svc_v1_desktop` 保持「纯消息」；契约 crate 才引入 mptp_rpc。
> 聚合层 `abs_kb_svc` 增加 `pub use abs_kb_svc_v1_desktop_rpc as desktop_rpc;`。

```rust
#![feature(impl_trait_in_assoc_type)]

#[rpc(path = "kb/v1", services = [TrHandshake, TrWorkspaceService, TrSessionService, TrGeneration])]
pub struct KbApiV1;

#[rpc(service = "workspace")]
pub trait TrWorkspaceService {
    fn list_workspaces<'f>(&'f self)
        -> impl TrMayCancel<'f, MayCancelOutput = RpcResult<WorkspaceList>>;
    fn add_workspace<'f>(&'f self, request: AddWorkspaceRequest)
        -> impl TrMayCancel<'f, MayCancelOutput = RpcResult<Workspace>>;
    fn remove_workspace<'f>(&'f self, workspace_id: WorkspaceId)
        -> impl TrMayCancel<'f, MayCancelOutput = RpcResult<Ack>>;
    fn rename_workspace<'f>(&'f self, workspace_id: WorkspaceId, name: String)
        -> impl TrMayCancel<'f, MayCancelOutput = RpcResult<Workspace>>;
}
// TrHandshake / TrSessionService / TrGeneration 同形
```

`Ack` / `KbRpcError` / 状态码映射：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, denco_macro::TrEncodable, denco_macro::TrDecodable)]
pub struct Ack;

pub enum KbRpcError<E> {
    /// 服务端明确拒绝；`code` 与 `message` 都从线上原样还原。
    Business(ErrorReply),
    /// 传输 / 解码 / 取消等失败；`E` 由具体传输给出。
    Transport(E),
}

/// 业务状态码命名空间：460–499，避开 MPTP/HTTP 已用的 400/404/500/504。
pub const K_BUSINESS_STATUS_BASE: u16 = 460;

pub fn status_of_error_code(code: ErrorCode) -> Status;
pub fn error_code_of_status(status: Status) -> Option<ErrorCode>;

/// 若这个 `RpcError` 是 460–466 的业务错误，剥离 Display 前缀并还原 `ErrorReply`。
pub fn business_error_from_rpc_(rpc: &RpcError) -> Option<ErrorReply>;
```

> 没有 `Outcome<T>`；契约 trait 直接返回 `RpcResult<T>`。
> 业务错误由服务端写成 `RpcError::Service`（带 460–466 状态码），客户端负责还原 `ErrorReply`。
> `KbRpcError<E>` 取代旧的 `RpcError<E>`：本地 `E = MptpIpcError`，跨机 `E = TcpError`。

### 5.3 服务端的四个薄包装

宏限制：同一个 impl 类型在同一 interface 下只能有一条 `TrRpcService` 实现。
因此 `KbService` 不再直接实现四个 trait，而由四个零成本包装各自实现一个：

```rust
pub struct KbHandshake(pub KbService);
pub struct KbWorkspace(pub KbService);
pub struct KbSession(pub KbService);
pub struct KbGeneration(pub KbService);

#[rpc(service_of(KbApiV1))]
impl TrWorkspaceService for KbWorkspace {
    fn list_workspaces<'f>(&'f self)
        -> impl TrMayCancel<'f, MayCancelOutput = RpcResult<WorkspaceList>>
    {
        ListWorkspacesAsync::new(&self.0)   // 复用现有 gen_mcf2 step 函数
    }
    // …
}
```

传输 crate 用四元组交接：

```rust
pub struct KbServiceSet<H, W, S, G> {
    pub handshake: H,
    pub workspace: W,
    pub session: S,
    pub generation: G,
}
```

`serve` 内部装配：

```rust
let KbServiceSet { handshake, workspace, session, generation } = services;
let router = Router::<SrvCfg, _>::new().call(move |ctx| {
    RpcRouter::<KbApiV1>::new(ctx)
        .add_service::<H>(move |_| handshake)
        .add_service::<W>(move |_| workspace)
        .add_service::<S>(move |_| session)
        .add_service::<G>(move |_| generation)
});
MptpServer::<SrvCfg, _>::new(router)
    .serve_listener_async(&mut binding, K_LISTEN_RESERVE).await
```

### 5.4 业务错误：460–466 状态码 + 客户端剥离前缀

问题：宏生成的服务端 dispatch 用 `err.to_string()` 写错误回复，`RpcError::Service` 的
Display 会加上 `"RPC 业务错误 {status}（{name}）："` 前缀，`ErrorReply.message` 会被污染；
而本轮不能改上游。

方案（Q4-B）：

1. **服务端**：业务失败写成 `RpcError::Service { status, message }`，其中
   - `status` = `460 + ErrorCode 的序号`（`BadRequest`=460 … `Internal`=466）；
   - `message` = `ErrorReply.message` 原文；
2. 宏写出 `reply_status_async(status, err.to_string())`；
3. **客户端**收到 `RpcError::Remote { status, body }`：
   - `status` 在 460..=466 → 按映射还原 `ErrorCode`；
   - 从 `body` 中找**第一个** `"）："`，取其后全部字节作为 `ErrorReply.message`；
   - 找不到分隔符 → 不伪造业务错误，按 `RpcError` 原样上报。

| `ErrorCode` | 状态码 |
| :--- | :--- |
| `BadRequest` | 460 |
| `NotFound` | 461 |
| `UnknownService` | 462 |
| `MissingApiKey` | 463 |
| `PluginOffline` | 464 |
| `Provider` | 465 |
| `Internal` | 466 |

```rust
// 契约 crate
pub const K_BUSINESS_STATUS_BASE: u16 = 460;
const K_DISPLAY_SEPARATOR: &str = "）：";

pub fn business_error_from_rpc_(rpc: &RpcError) -> Option<ErrorReply> {
    let RpcError::Remote { status, body } = rpc else {
        return Option::None;
    };
    let code = error_code_of_status(*status)?;
    let message = strip_business_message_(body)?;
    Option::Some(ErrorReply { code, message })
}

// 各传输自行决定怎么包 Transport：
// 本地：rpc -> KbRpcError::<MptpIpcError>::Transport(MptpIpcError::Rpc(rpc))
// 跨机：Reply::Error(reply) -> KbRpcError::<TcpError>::Business(reply)
```

风险与守门：

- 依赖上游 `RpcError::Service` 的 Display 格式。**加一条单元测试**：
  构造 `RpcError::Service{ status: 461, message: "x：y" }`，断言
  `business_error_from_rpc_(&RpcError::Remote{ status, body: err.to_string().into_bytes() })`
  能还原出 `ErrorReply{ code: NotFound, message: "x：y" }`。上游文案一改，这条测试先红。
- 消息本身含 `"）："` 时，`split_once` 取**第一个**分隔符（即前缀那个），余下原样保留。
- 客户端只用 460..=466 判定业务错误；MPTP 路由的 404/405、传输的 500/504 不会被误判。

> 与 v2 早期方案的区别：不再引入 `Outcome<T>`，契约 trait 保持 `RpcResult<T>`。
> 代价是依赖 Display 前缀；收益是签名不变、`RpcError` 的传输/业务分层仍可用。

服务端内部故障（存储 I/O、解码后的意外）仍翻成 `ErrorReply { code: Internal, message }`，
与旧 `business_reply_` 的语义一致。

### 5.5 编解码矩阵（denco-only）

| 通道 | 编码 | 写入方式 | 读取方式 | 兼容性 |
| :--- | :--- | :--- | :--- | :--- |
| MPTP RPC body | `mp_denco` | 框架的 ring，流式 | 框架的 ring，流式 | 新协议，无旧版本 |
| 跨机 TCP 帧载荷 | `mp_denco` | `encode_to_vec`（增长缓冲，上限 8 MiB） | `MpDecoder` over slice | 网关/客户端同版本升级；旧 postcard 不兼容 |
| 本地存储 | `mp_denco` | `encode_to_vec`（增长缓冲，上限 64 MiB）→ tmp + rename | `MpDecoder` over 文件字节 | **不兼容旧 JSON**；扩展名 `.mp` |
| stdout 通知 | `json_denco` | 4 KiB 栈缓冲 → 一行 stdout | `JsonDecoder` over 行字节 | 与旧 JSON 形状一致（便于日志） |
| CLI 展示 | `json_denco` | 直接打印一段 JSON | – | 仅人读；紧凑输出 |
| 用户配置 | serde + toml（Q5） | 不变 | 不变 | 不变 |
| rig 第三方 JSON | serde_json（Q5） | 不变 | 不变 | 不变 |

- 存储与 TCP 帧都用 MessagePack；`json_denco` 只用于 stdout 通知与 CLI 展示。
- 存储文件扩展名从 `.json` 改为 `.mp`；旧 `.json` 文件不再被扫描/读取（Q6）。
- `json_denco` 不提供 pretty 输出，CLI 的 JSON 是紧凑的。

### 5.6 客户端门面

`kb_svc_mptp_ipc::Client` 用**固有方法**暴露窄接口（不实现契约 trait，避免把
`RpcResult` 与业务/传输两层错误泄漏给调用方）：

```rust
impl Client {
    pub fn connect(runtime_dir: impl AsRef<Path>) -> Result<Self, MptpIpcError>;
    pub fn connect_with_timeout(runtime_dir: impl AsRef<Path>, timeout: Duration) -> Result<Self, MptpIpcError>;

    pub fn list_workspaces<'f>(&'f self) -> WaitAsync<'f, 'f, WorkspaceList>;
    pub fn add_workspace<'f>(&'f self, request: AddWorkspaceRequest) -> WaitAsync<'f, 'f, Workspace>;
    // … 其余方法
}
```

每个方法：

```rust
fn list_workspaces<'f>(&'f self) -> WaitAsync<'f, 'f, WorkspaceList> {
    self.submit_(move |sender| Box::new(move |client| Box::pin(async move {
        let result = client.call::<KbApiV1>().list_workspaces().await;
        let _ = sender.send(result.map_err(|rpc| match business_error_from_rpc_(&rpc) {
            Option::Some(reply) => KbRpcError::Business(reply),
            Option::None => KbRpcError::Transport(MptpIpcError::Rpc(rpc)),
        }));
    })))
}
```

- `WaitAsync<'f, 'f, T>` 的输出是 `Result<T, KbRpcError<MptpIpcError>>`；
- `Job = Box<dyn FnOnce(Rc<MptpClient<CliCfg>>) -> Pin<Box<dyn Future<Output = ()>>> + Send + 'static>`；
- 闭包只捕获 Send 的请求与 oneshot sender；借用 `MptpClient` 的 future 在宿主线程内构造；
- 等待用 `gen_mcf2` 展开的 `WaitAsync`，同时轮询 oneshot 与取消令牌；
- 取消语义与现状一致：只放弃等待，不撤回请求；宿主侧用 `NonCancellableToken` 跑完；
- `Client` 只持 `futures_channel::mpsc::UnboundedSender<Job>` 等少量字段，保持 `Send + Sync`。

错误归类：

```text
Remote{status ∈ 460..=466, body} 且能剥离前缀 → KbRpcError::Business(ErrorReply{code, message})
其它 RpcError                                  → KbRpcError::Transport(MptpIpcError::Rpc(rpc))
```

`KbRpcError<E>` 由契约 crate 定义；本地 `E = MptpIpcError`，跨机 TCP `E = TcpError`。
conn_mgr / rproxy 共用它来保持「业务失败 vs 传输失败」的旧分层。

## 9. 风险与待拍板

### 9.1 过渡期 serde（Q1）

旧 `kb_svc_servo_ipc` 用 ipc-channel（postcard/serde）序列化协议类型。
在它被删除之前，**协议类型必须保留 serde 派生**，否则旧路径编不过。

- 推荐：P0–P7 期间协议类型 **serde + denco 双派生**；P8 删旧 crate 后一次性移除 serde；
- 代价：过渡期两套属性并存，需要测试同时守 serde 与 denco；
- 备选：P0 就删旧 crate，接受新传输完成前不能编译（不推荐）。

### 9.2 配置与 rig 的 serde 例外（Q5）

- `kb_client_config` 的 TOML 是**给人手改**的配置，`toml` crate 依赖 serde；改 denco 意味着
  换成 JSON、丢掉注释。推荐保留。
- `kb_rig_llm_v1_adapt` 用 `serde_json::Value` 解析 provider 的任意 JSON，rig 本身也依赖 serde；
  推荐保留。其**自有协议类型**（`TextDelta` / `ToolCall` / `Usage` / `AdaptedEvent` /
  `PluginRequest` / `PluginEvent`）改为 denco；`abs_llm` 才能彻底去 serde。

### 9.3 存储格式与旧数据（Q6）

- 存储从 `serde_json` 改为 `mp_denco`，文件扩展名从 `.json` 改为 `.mp`；
- **旧 `.json` 文件不再被扫描/读取**；如果仓库外有需要保留的用户数据，另行一次性迁移；
- 因此协议类型不需要为旧 JSON 保留 `#[denco(rename_all)]` / `#[denco(default)]`；
  只为可读性保留 `IpcReadyNotice` 的 `"ipc_ready"`；
- `#[denco(transparent)]` 仍要加（id 与 `Capabilities` 编码成裸值，而不是单元素数组）；
- CLI 输出用 `json_denco`（紧凑），仅人读。

### 9.3.1 业务错误前缀的风险（Q4）

- 客户端依赖 `RpcError::Service` 的 Display 文本：`"RPC 业务错误 {n}（{name}）：{message}"`；
- 守门测试：构造 460–466 状态码的 `RpcError::Service`，断言 `to_string()` 能被
  `strip_business_message_` 还原出原文（含 message 自身带 `）：` 的用例）；
- 该测试失败即说明上游文案变了，必须重新评估剥离逻辑；本轮固定 rev，风险可控。

### 9.4 跨机 TCP 兼容（Q3）

- 帧载荷从 postcard 换成 mp_denco 后，**旧远程客户端无法连新网关**；
- 网关与 `TcpClient` 在同一仓库、同版本发布，可接受；
- 如果必须兼容旧客户端，只能保留 postcard（违反 D0），或加一个版本协商/双解码回退（超出本轮）。

### 9.5 其它风险

| 风险 | 缓解 |
| :--- | :--- |
| 单个进程内运行时必须一致 | 每个进程关掉 `rpc_core_v1` 默认的 `rt-tokio`，显式点亮 `rt-compio`；跨进程（plugins）不要求统一 |
| UDS 路径 107 字节上限 | bind 前检查并返回 `PathTooLong` |
| connect + 握手总超时 | `compio::time::timeout` 包住整段；重试间隔 20ms |
| 一次一个连接导致第二个客户端等待 | 保持现状并写进文档；UDS backlog 会接住连接 |
| 方法/字段顺序是线上契约 | 契约 crate 文档写明「只允许末尾追加」 |
| `#[rpc(service_of)]` 跨 crate | 宏生成隐藏模块是 `#[doc(hidden)] pub mod`，P3 最小验证 |
| 上游 Display 文案变化导致前缀剥离失效 | P3 加「钉住前缀格式」的单测；固定 mptp_rpc rev |
| mp 存储不可读 / 无旧数据 | Q6 已接受；文档写明 `.mp` 与不兼容 |
| 大存储文件的编码缓冲 | 增长缓冲 + 64 MiB 上限；超限明确报错 |
